## 1. 目标

本文用于指导 Scenara Core 的规范整改和数据平台拆分，解决以下问题：

1. 明确 Core 是共享控制面和生产运行仓库，不承担模型训练和完整数据治理。
2. 修正跨仓库能力 ID、契约、错误码、事件、对象引用、时间和日志格式。
3. 打通模型制品从准入清单到真实运行时安装的执行链路。
4. 建立符合总体规范的人物检索返回契约。
5. 将现有 Dataset、Dataset Version、Annotation 等数据治理能力迁移到 `scenara-data`。
6. 在拆分期间保持 Console、API、SDK、ID、权限和审计兼容。

本文不要求 Core 实现 Training Job、Experiment、FastReID 训练和模型评估。这些能力属于 `scenara-model`。

## 2. Core 最终职责

Core 保留：

```text
统一 Console / API Gateway / SDK
Organization / Project / IAM / Permission / Audit
Media / Stream Source
Run / Pipeline / Operator / Result
Person / Track / Feature / FeatureStore
Person Search / Track Search
Model Admission / Activation / Deployment / Rollback
Feedback Review
Hard Sample Qualification and Export
Product Catalog / Repository Topology / Contract Catalog
```

Core 不再拥有：

```text
Dataset 事实来源
Dataset Version 事实来源
Sample / Annotation
Data Quality / Data Lineage
Dataset Builder / Import / Export
Hard Sample 数据集入库
训练任务、实验、训练评估和模型制品生成
```

## 3. 优化总清单

| 编号 | 优先级 | 优化项 | 当前问题 | 目标结果 |
| --- | --- | --- | --- | --- |
| CORE-001 | P0 | 平台能力 ID 统一 | 对外存在 `body_reid`、`body_embedding` 等内部名称 | 对外统一 `person_reid`，内部能力通过映射保留 |
| CORE-002 | P0 | Contracts 权威来源 | Core 内存在契约发布镜像，容易被误认为事实来源 | Core 只消费和镜像正式发布契约，CI 验证零漂移 |
| CORE-003 | P0 | 错误码目录 | 错误码分散在服务和异常处理代码中 | 所有公共错误码在 Contracts 登记并有映射测试 |
| CORE-004 | P0 | 事件目录和信封 | 当前事件以功能实现为主，缺统一事件信封 | 事件具备版本、租户、项目、请求、追踪和幂等信息 |
| CORE-005 | P1 | RFC 3339 时间 | 多个 API 模型使用 Unix 浮点秒 | 公共 API 和事件统一 UTC RFC 3339 |
| CORE-006 | P1 | 结构化日志 | 当前使用 `created_at`、`logger`、`traceparent` | 增加 `timestamp/service/module/trace_id`，保留兼容字段 |
| CORE-007 | P1 | 跨仓库对象引用 | 模型和数据引用仍以 URI、ID 或内部 key 为主 | 对外统一 ObjectReference，读取时验证摘要 |
| CORE-008 | P1 | 模型制品安装 | 准入和激活已有，实际加载依赖预配置本地模型 | 自动解析、下载/挂载、校验、安装和健康检查 |
| CORE-009 | P1 | Person Search 契约 | 身份、轨迹、媒体和时间分散在不同接口 | 单次图片检索返回 Person/Track/Media/Time/Similarity/Model Version |
| CORE-010 | P1 | 数据平台 Client 端口 | DatasetService 直接依赖 Core StateStore 和 MediaAsset | 领域层依赖 DataPlatformClient，不再访问 Data 业务表 |
| CORE-011 | P2 | Dataset 数据迁移 | Dataset 表位于 Core PostgreSQL | 数据迁移到 Data 独立数据库，Core 旧表只读后退役 |
| CORE-012 | P2 | Annotation 拆分 | Annotation Task/Provider 混在通用 Control Plane | 迁移到 Data，Core 仅保留代理和产品目录入口 |
| CORE-013 | P2 | Hard Sample 对接 | Core 只生成清单，尚无 Data 正式接收闭环 | Core 导出，Data 幂等接收并形成 Sample/Dataset Version |
| CORE-014 | P2 | Console/API/SDK 兼容 | Dataset 页面和客户端直接调用 Core 本地 API | 公共路径不变，由 Core 网关代理 Data |
| CORE-015 | P1 | 前端设计令牌收敛 | 全局样式仍使用旧变量名，各 Vue 页面存在大量硬编码颜色 | 建立共享语义令牌并保留旧变量兼容期，业务组件不再新增未登记颜色 |
| CORE-016 | P1 | 平台主题绑定 | Console 当前只有 Core 视觉基线，没有 `data-platform` 与路由平台主题 | 根节点按路由绑定 Core/Data/Model/Contracts 主题，仅覆盖受控强调色 |
| CORE-017 | P1 | 响应式与无障碍 | 未提供跳到主内容入口，部分移动端图标控件小于 44px，自动明暗色声明与实际实现不一致 | 补齐键盘路径、触控尺寸、焦点和对比度门禁，未实现暗色模式前固定浅色方案 |
| CORE-018 | P2 | 前端视觉回归证据 | 现有 E2E 以行为断言为主，缺少四种规范视口的主题和布局截图门禁 | 为关键路由增加桌面、平板、移动端截图与溢出检查 |

## 5. 需要迁移到 Data 的现有实现

### 5.1 Dataset 与 Dataset Version

当前来源：

```text
scenara/platform/dataset.py
scenara/platform/models.py 中 Dataset* 模型
scenara/platform/store.py 中 Dataset 持久化端口
scenara/infrastructure/memory_state.py
scenara/infrastructure/postgres_state.py
migrations/0007_dataset_governance.sql
tests/test_dataset.py
```

目标处理：

1. `DatasetService` 的业务规则迁移到 Data。
2. Dataset 公共 DTO 迁移到 Contracts；Data 内部持久化模型不得反向进入 Core。
3. `scenara_datasets`、`scenara_dataset_versions` 表迁移到 Data PostgreSQL。
4. Core 删除本地写入端口，改用 `DataPlatformClient`。
5. Core 可以在兼容期保留只读 Adapter 和数据导出工具。

### 5.2 Annotation Task 与 Provider

当前来源：

```text
scenara/platform/control_plane.py 中 AnnotationProvider、AnnotationTask
scenara/server.py 中 /api/v1/data/annotation-* 路由
通用 Control Plane Record 持久化
frontend/console/src/views/GovernanceView.vue 中相关界面
```

目标处理：

1. Annotation Provider、Task、Assignment、Review 迁移到 Data。
2. Data 建立明确表结构，停止使用无领域约束的通用 JSON Record 作为长期事实来源。
3. Core 保留路由代理、统一认证和 Console 页面。
4. 审计事件由 Data 产生，通过正式事件或审计接收 API 回传 Core。

### 5.3 Data Quality 与 Data Lineage

当前 Dataset Version 仅保存：

```text
quality_score
lineage JSON
annotation_summary JSON
```

这些字段只能作为迁移输入。Data 必须建立一等资源：

```text
QualityReport
QualityRule
QualityIssue
LineageEdge
SourceReference
AnnotationSummary
```

已发布 Dataset Version 引用固定的 QualityReport 和 Lineage Snapshot，不直接嵌入可变 JSON 事实。

### 5.4 Hard Sample

拆分后职责：

| 动作 | Core | Data |
| --- | --- | --- |
| 产生推理结果 | 负责 | 不负责 |
| 接收人工反馈 | 负责 | 不负责 |
| 判断是否批准、授权和脱敏 | 负责 | 不负责 |
| 生成不可变 HardSampleManifest | 负责 | 消费 |
| 幂等接收 Manifest | 不负责 | 负责 |
| 创建 Sample 和 Annotation Task | 不负责 | 负责 |
| 构建新 Dataset Version | 不负责 | 负责 |
| 向 Model 发布 DatasetVersionReference | 不负责 | 负责 |

## 6. 不得迁移到 Data 的内容

以下数据与服务不得随 Dataset 拆分迁移：

```text
Core MediaAsset 业务记录
Stream Source
Run 和 Pipeline
Result 和 Result Shard
Person 和长期身份
Track 和生产轨迹
Feature 和 FeatureStore
Search Index
Feedback 审核事实
Model Runtime Binding
IAM、API Key、Membership 和 Role
Core Audit 查询事实
```

Data 可以保存这些资源的稳定引用和必要快照，但不得复制其业务事实来源。

## 7. DataPlatformClient 设计

Core 新增领域端口，建议能力如下：

```python
class DataPlatformClient(Protocol):
    async def create_dataset(...): ...
    async def get_dataset(...): ...
    async def list_datasets(...): ...
    async def create_dataset_version(...): ...
    async def publish_dataset_version(...): ...
    async def get_dataset_version_reference(...): ...
    async def submit_hard_sample_manifest(...): ...
    async def get_annotation_task(...): ...
```

实现分为：

```text
LocalDataPlatformAdapter
    兼容现有 StateStore，仅用于迁移期

HttpDataPlatformClient
    调用独立 scenara-data API，作为最终生产实现
```

Client 必须处理认证、超时、重试、幂等、错误码映射、请求 ID 和追踪上下文。领域服务不得直接使用通用 HTTP Client。

## 8. 数据迁移策略

推荐流程：

1. 导出现有 Dataset、Dataset Version 和 Annotation 记录。
2. 解析所有 `asset_ids`，生成来源引用和对象摘要。
3. 对已发布版本生成不可变 Manifest；无法验证摘要的版本不得自动标记为已发布。
4. 保留现有 `dataset_id`、`version_id` 和版本字符串。
5. 将数据导入 Data 独立数据库和 `scenara-datasets` 对象空间。
6. 比对记录数、版本数、Manifest 摘要、权限和审计引用。
7. 启用影子读，比较 Core 本地结果与 Data API 结果。
8. 进入短时写冻结或使用 Outbox 同步最后增量。
9. 切换 Core 到 `HttpDataPlatformClient`。
10. Core 旧表只读观察至少一个约定发布周期，再移除写路径。

禁止长期双写。发生回滚时，只允许在明确回滚窗口内恢复 Core 本地写入，并处理 Data 侧已产生的增量记录。

## 9. API、Console 和 SDK 兼容

外部公共路径优先保持：

```text
/api/v1/datasets
/api/v1/datasets/{dataset_id}
/api/v1/datasets/{dataset_id}/versions
/api/v1/dataset-versions/{version_id}/transition
/api/v1/data/annotation-*
```

这些路径由 Core 转发到 Data。新 Data 内部 API 可以使用 `/internal/v1` 或独立服务地址，但不得直接暴露第二套登录和租户参数。

Console 的 Dataset 和 Annotation 页面继续保留在 Core。前端不需要知道 Data 的部署地址。

SDK 继续从 Core OpenAPI 生成。Data 可以单独发布服务间 SDK，但不得替代平台公共 SDK。

### 9.1 Console 主题接入

数据拆分不改变统一 Console 架构。前端主题按路由所属平台绑定：

```text
Core 生产与控制面页面 -> data-platform="core"
Dataset / Annotation / Quality / Lineage 页面 -> data-platform="data"
Experiment / Training / Evaluation / Registry 页面 -> data-platform="model"
Contract Catalog / Schema 页面 -> data-platform="contracts"
```

实施顺序：

1. 在 `frontend/console/src/styles.css` 建立总体规范定义的语义令牌，并把现有变量映射到新令牌。
2. 在路由元数据中登记 `platform`，由根布局设置唯一的 `data-platform`。
3. 逐页替换无语义硬编码色；品牌 SVG 固定颜色和经登记的图表序列色除外。
4. 将 `color-scheme` 固定为 `light`，直至完整暗色主题通过 ADR 和验收。
5. 增加跳到主内容入口、移动触控尺寸、`prefers-reduced-motion` 和四种视口测试。

该整改与 Data 服务拆分可以并行，但不得改变 Dataset 公共路径、页面信息架构或跨仓库权限含义。

## 10. 验收条件

数据拆分完成必须同时满足：

```text
Core 不再写 Dataset 和 Annotation 业务表
Data 有独立数据库、迁移、备份和恢复流程
公共 API 和 SDK 兼容测试通过
所有已发布 Dataset Version 摘要验证通过
租户、项目和权限隔离测试通过
HardSampleManifest 幂等接收测试通过
Data 到 Model 的 DatasetVersionReference 测试通过
Core 到 Data 的请求 ID 和追踪链路可查询
迁移数据数量和摘要报告已归档
回滚演练完成
Console 主题跟随路由平台且不出现第二套导航或登录
四种规范视口截图、键盘路径和颜色对比度验证通过
```

| 批次 | 内容 | 前置条件 |
| --- | --- | --- |
| A | Contracts、能力 ID、错误码、事件信封 | 无 |
| B | 时间、日志、对象引用 | A |

## 12. 明确不同时实施的变更

数据拆分期间不得同时执行：

```text
批量修改现有业务 ID
修改公共 Dataset API 路径
替换 Vue Console
重写统一 IAM
改变已发布 Dataset Version 的含义
迁移 Person、Track、Feature 或 Feedback 所有权
引入长期双写
```

将这些变更与拆仓解耦，才能保证问题可定位、数据可校验、故障可回滚。
